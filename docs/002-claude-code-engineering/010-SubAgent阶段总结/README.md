## 结论先行：SubAgent 到底在解决什么？

经过六讲的学习，可以给出一句话结论——

**SubAgent 解决的不是「能力问题」，而是「工程风险」。**

具体来说，它不是在让 AI 变得更聪明，而是在解决五个工程风险：

| 工程风险 | SubAgent 提供的机制 | 对应章节 |
|---------|-------------------|---------|
| **上下文污染** — 执行噪声淹没决策信息 | 独立上下文窗口，执行完即释放 | 005 高噪声 |
| **权限越界** — 「我只是让你看看，你却改了代码」 | 工具权限白名单/系统级硬约束 | 004 只读型 |
| **角色混乱** — 一个人又当裁判又当运动员 | 职责边界 + 权限递进 | 004 概念、006 流水线 |
| **锚定偏见** — 找到一个解释就停止探索 | 竞争假设 + 多视角互相挑战 | 007 Agent Teams |
| **经验散落** — 好的做法用一次就丢了 | 可版本化配置文件 + 团队共享 | 004 概念 |

这五个风险的共同特征：**不是 AI 「做不了」，而是 AI 「做起来容易出事」**。SubAgent 是用工程结构去兜底这些风险。

## 两层模型：结构化分工 → 协作型认知

黄佳老师把整个 SubAgent 体系分为两层：

```
第一层：Sub-Agents（结构化分工）
      解决"单脑如何安全分工"——上下文隔离、权限控制、职责拆分
            │
            │ 当任务之间不只是「执行依赖」而是「认知依赖」时
            ↓
第二层：Agent Teams（协作型认知）
      解决"多脑如何互相挑战"——辩论、跨视角发现、竞争假设
```

**Sub-Agent 的应用场景**：上下文污染、权限边界、高噪声干扰、阶段性分工、可控编排。

**Agent Teams 的应用场景**：锚定偏见、单视角误判、过早收敛（找到一个 bug 就停了）、决策质量不足。

## 四种使用模式：你该用哪个？

### 单独使用

| 类型 | 适合场景 | 权限 | 模型 | 关键设计 |
|------|---------|------|------|---------|
| **只读型** | 代码审查、影响面分析 | Read/Grep/Glob | sonnet | 不给 Edit/Write |
| **高噪声型** | 测试运行、日志分析 | Read/Bash | haiku/chat | 结论先行输出格式 |

### 编排使用

| 模式 | 适合场景 | 判断标准 | 核心风险 |
|------|---------|---------|---------|
| **并行探索** | 各自独立的多模块分析 | 任务间无信息依赖 | 跨模块关联遗漏 |
| **流水线编排** | 有依赖的阶段式任务 | 阶段间需要交接 | 交接信息丢失 |
| **混合模式** | 部分独立+部分依赖 | Fan-out→Fan-in 等三种形态 | 复杂度增加 |

### Agent Teams

| 模式 | 适合场景 | 核心机制 |
|------|---------|---------|
| **竞争假设** | 根因不明，多方向验证 | 辩论淘汰 |
| **分层评审** | PR Review，多维度 | 并行审查 |
| **模块化开发** | 多人分工写代码 | 任务依赖+文件所有权 |
| **规划-审批** | 高风险任务 | 先交方案再执行 |

## 选型决策树（完整版）

```
你的任务是什么特征？

├── 需要多个 workers 吗？
│   └── 否 → 单 Agent 或主对话直接处理
│
├── Workers 需要互相通信吗？
│   ├── 否 → Sub-Agent
│   │   ├── 单任务 → 单独使用（只读型/高噪声型）
│   │   └── 多任务
│   │       ├── 独立 → 并行探索
│   │       └── 有依赖 → 流水线 + 交接契约
│   │
│   └── 是 → Agent Teams
│       ├── 根因不明 → 竞争假设
│       ├── 多维度审查 → 分层评审
│       ├── 多人写代码 → 模块化开发
│       └── 高风险改动 → 规划-审批
```

## 设计 SubAgent 的核心方法论

不来自某一讲，而是贯穿六讲的共同主线：

### 1. 痛点驱动设计（005 只读型）

```
工程痛点 → 分析缺什么能力 → 设计职责边界 → 选择工具组合 → 配置子代理
```

不是从「CC 有哪些机制」出发，而是从「我的代码在哪会出问题」出发。

### 2. 信噪比决策（007 高噪声）

```
输出 > 50 行 + 你只关心 < 10 行 → 用子代理
```

不仅是 token 省钱，更重要的是注意力质量——噪声留在主对话会影响回答质量。

### 3. 权限递进 + 关键审批点（006-008）

```
探索 → 分析 → [人工审批] → 修复 → 验证
只读    只读       ↑        读写     执行
                  读写跨越点
```

只给必要的工具，在「只读到读写」的跨越点设人工防线。

### 4. 交接契约（008 流水线）

每个阶段的 Handoff 必须让下一阶段**无需重复上游工作**。交接信息量 = 下一阶段能否直接开始。

### 5. 失败回退原则（008 流水线）

```
Verifier 失败 → 回退到 Analyzer（不是让 Fixer 重试）
新证据应该反馈给分析者，不是执行者
```

## 贯穿始终的工程原则

不来自原文，来自六讲学习的综合理解：

### 1. 最小权限

只给需要的工具，不多给一个。Read 能完成的就不给 Edit。Code-reviewer 给了 Bash 但不是为了写文件——是为了 `git diff`。

### 2. 职责分离

审查的不管修复，定位的不管分析，Fixer 不判断方向。一个人只做一件事，边界清晰。

### 3. 渐进演进

不是一开始就知道该用什么。黄佳老师自己先做 Demo，感觉吃不消了才考虑架构。LangChain 的原则：「Start with a single agent. Add tools before adding agents.」

### 4. 模型与任务匹配

```
haiku/deepseek-chat  → 执行命令、模式匹配、模板填充
sonnet/deepseek-v4-pro → 分析推理、关联发现、根因判断
```

不是所有任务都需要最强模型——省钱也是工程能力。

### 5. 知识注入 > Prompt 提示

SubAgent 的 `skills` 字段是系统级注入（启动时就带着知识），比 Prompt 里写「请参考 doc/xxx.md」可靠得多。

## 原文综合案例：支付超时排查五阶段

这是加餐文章中最有价值的内容——用一个完整案例把全部模式串起来：

```
Phase 1: 并行探索（只读）
    payment-explorer ∥ order-explorer ∥ infra-explorer
    → 综合三份报告，了解全局

Phase 2: 并行高噪声处理（只读）
    log-analyzer ∥ test-runner
    → 日志分析 + 测试结果，收集线索

Phase 3: 假设竞争（Agent Teams）
    四个侦探各自调查 + 互相通信 + 挑战结论
    → 拼出级联故障链

Phase 4: 流水线修复（读写开始）
    Locator → Analyzer → [人工审批] → Fixer → Verifier
    → 这是唯一有写权限的阶段

Phase 5: 并行验证（只读+执行）
    test-runner ∥ performance-checker ∥ code-reviewer
    → 全量回归确认修复有效
```

**注意权限变化**：只有 Phase 4 的 Fixer 有写权限，其余全部只读。这就是「最小权限」在复杂场景中的落地。

## 我在六讲学习中的关键收获

以下不来自原文，来自我自己学习和实操的反思：

1. **SubAgent 的价值不是并行加速**。评论区多次澄清——Ctrl+B 只是结构上的并行，不是执行层面的并行。核心价值是隔离和约束。

2. **学配置不如学思维**。六讲下来，每个子代理的配置细节都不一样，但「痛点→缺什么→选什么」这套思维框架是一贯的。会写一个 code-reviewer 不厉害，掌握了这套框架才厉害。

3. **模型分层真的能省钱**。我们用 `deepseek-chat` 做 article-fetcher 和 comment-filter，用 `deepseek-v4-pro` 做写笔记的主对话——这就是正文里说的「给不同任务配不同价位的模型」。

4. **交接契约是流水线最难的部分**。不是把任务拆成四步就叫流水线——如果 Analyzer 收到 Locator 的输出后还要重做一遍 Grep，那流水线就是形同虚设。信息传递质量比阶段数量重要得多。

5. **Agent Teams 对国内模型兼容性存疑**。评论区有读者报告用国内模型跑 Teams 报 `API Error: Not supported model claude-opus-4-6`——这对我们的 DeepSeek 场景是个重要提醒。
